# Реальные покупки: контракт подключения

Игра сейчас продаёт товары только за обычные монеты. `data/social/commerce_policy.json` явно выключает реальные платежи; покупаемые дублоны не создаются из локального сохранения. Редкие осколки остаются наградной валютой. Интерфейс не имитирует оплату и не предлагает вводить банковские данные.

`server/commerce/ledger.py` — проверяемая основа серверного учёта постоянных украшений: заказ с ценой из серверного каталога, ключ повторного запроса, подтверждение через серверный адаптер провайдера, однократная выдача, восстановление по аккаунту, отзыв после возврата и журнал. Серверного HTTP-сервиса, платформенного адаптера и развёртывания пока нет. Пример каталога выключен, цены не назначены. Тестовый провайдер используется только в unittest.

Последовательность будущего подключения:

1. Выбрать первую платформу (Steam или Android) и поддерживаемые страны/валюты, получить ID приложения и серверные полномочия. Реальные цены назначаются отдельно.
2. Аутентифицированный сервер выводит ID аккаунта из подтверждённой сессии платформы. Поле account_id из запроса клиента не считается аутентификацией.
3. Клиент запрашивает заказ: product_id и idempotency_key. Сервер определяет состав, цену и валюту; отвечает order_id и платформенными данными оплаты. Клиент не задаёт сумму или предметы выдачи.
4. Платформа запрашивает подтверждение владельца кошелька. Сервер проверяет платёж через API платформы; callback клиента или локальный флаг «оплачено» не являются доказательством.
5. После подтверждения операция выдачи фиксируется атомарно. Повтор запроса не выдаёт предмет повторно. Для восстановления сервер возвращает собственные подтверждённые права текущего аккаунта.
6. Для возвратов используется подтверждённый статус провайдера и отзыв соответствующей выдачи. Повторная проверка старой успешной квитанции не отменяет возврат.

Для Steam ориентир — [официальная схема Steamworks](https://partner.steamgames.com/doc/features/microtransactions/implementation). Секреты не размещаются в Godot, JSON репозитория, сохранении или логах. Серверную БД, сессии, ключи и резервные копии держать вне репозитория. Обычный офлайн-режим остаётся работоспособным без сервера.

Ещё требуются: адаптер платформы, авторизация аккаунтов, HTTPS и эксплуатационное развёртывание, проверка возвратов, интеграционные тесты в sandbox платформы, отдельный серверный учёт срока премиума и сезонных платных прав, согласованные цены и поддержка покупок. Текущие офлайн-предметы не превращаются автоматически в официальные серверные активы.
