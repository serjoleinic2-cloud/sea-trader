## С чего начать

1. Проверь, что открыт именно указанный репозиторий и ветка. Инструкции PowerShell для получения ветки находятся в корневом `README.md`. Не переноси изменения в `main` и не создавай копию репозитория для задачи.
2. Прочитай `rules/PROJECT_STATE.md`: это текущий снимок сделанных механик, ограничений и незавершённых задач.
3. Прочитай `rules/TRUTH.md` и `rules/AI_DEVELOPMENT_RULES.md`: обязательные правила игры и работы с кодом.
4. Для конкретной задачи открой соответствующую часть `rules/ARCHITECTURE.md`, `rules/DATA_SCHEMA.md`, `rules/DEVELOPER_GUIDE.md`, данные и существующие тесты.
5. Перед правками проверь статус Git. Сохраняй незакоммиченные изменения пользователя; не стирай и не переписывай их вслепую.

Если этот файл и актуальный код или `rules/PROJECT_STATE.md` расходятся, ориентируйся на актуальное состояние проекта и сообщи о найденном расхождении.

## Коротко о проекте

Sea Trader — офлайн-игра на Godot 4, GDScript. Игрок вручную управляет торговым кораблём, исследует процедурный мир, посещает порты, торгует и развивает собственную базу и флот. Механики важнее финальной графики. Сеть и серверная зависимость не входят в архитектуру.

Основной игровой цикл: **база → производство и рынок → груз → ручной рейс → прибыль → развитие**. Автоматизация открывается после изучения маршрута вручную.

## Как запускается игра

- `project.godot` — настройки проекта, автозагрузки и стартовая сцена.
- `scenes/game/main.tscn` — корневая игровая сцена.
- `scripts/main.gd` — создаёт мир и корабль, запускает загрузчик модулей и связывает сцену с игровыми системами.
- `core/module_loader.gd` + `data/config/game_modules.json` — реестр, зависимости, порядок запуска систем и окон. При добавлении модуля сначала проверь и дополни реестр; не создавай отдельную параллельную регистрацию в Main.

## Где находятся части игры

| Путь | Назначение |
| --- | --- |
| `autoloads/game_state.gd` | Единственное runtime-состояние игрока и мира. |
| `autoloads/save_system.gd` | Локальные сохранения, восстановление и миграции. Любой доступ к сохранению проходит здесь. |
| `autoloads/event_bus.gd` | Сигналы между системами; не связывать UI напрямую с чужими окнами, если подходит событие или системный API. |
| `autoloads/game_data.gd` | Загрузка статических JSON-определений через `GameData`. |
| `core/` | Загрузчик модулей и проверка конфигурации; здесь не размещают игровую экономику. |
| `systems/<область>/` | Правила механик: мир, порты, строительство, верфь, флот, торговля, контракты, карьера, персонал, события и бои. |
| `systems/ui/` | Экраны и HUD. UI отображает состояние и отправляет команды системам; правила, цены, материалы и сохранения остаются в системах. |
| `data/` | Каталоги и баланс в JSON. Это источник статических определений, а не runtime-прогресса. |
| `scenes/` | Сцены Godot и узлы представления корабля/мира. |
| `assets/` | Визуальные, аудио- и шрифтовые ресурсы. |
| `tests/` | Unit, интеграционные, smoke- и экономические проверки. |

## Текущие точки для строительства и верфи

Логика уже разделена на существующие системы. Расширяй их, не добавляй второй BuildingSystem или ShipyardSystem.

| Действие | Файл / API |
| --- | --- |
| Список зданий на базе и нижняя навигация порта | `systems/ui/port_window.gd`: `_rebuild_building_list()`, `_open_section()`, `_plan_selected_building()` |
| Материалы, требования, ранги, таймеры и завершение здания | `systems/buildings/building_project_system.gd` |
| Каталог зданий и рецепты | `data/ports/building_catalog.json`, `data/ports/building_rules.json` |
| Окно выбранного строительного проекта | `systems/ui/building_project_window.gd` |
| Событие завершения здания | `EventBus.building_activated`; на него уже подписывается `PortWindow` |
| Доступ к разделу флота | `systems/ui/window_coordinator.gd`: пункт «Флот и верфь» находится в меню «ЕЩЁ» и показывается при наличии активной верфи или дополнительного корабля |
| Каталог корпусов, допуски и материалы кораблей | `data/ships/ship_catalog.json` |
| Доступ/создание корабля во флоте | `systems/fleet/fleet_system.gd` |
| Передача материалов, имя, отмена и завершение корабельного проекта | `systems/shipyard/shipyard_system.gd` |
| Список корпусов и окно ресурсов/постройки | `systems/ui/fleet_window.gd`, `systems/ui/shipyard_window.gd` |

### Известный текущий путь игрока

В меню порта открывается раздел **«Строительство»**. Сейчас здания выводятся текстовыми кнопками в списке; выбор здания и кнопка открытия проекта — отдельные действия. Окно проекта показывает характеристики, требования и передачу материалов ползунками; запуск недоступен, пока не собраны все материалы. Стройка завершается по таймеру.

После постройки верфи отдельной вкладки **«Верфь»** в меню строительства сейчас нет. Чтобы строить корабль, нужно открыть **«ЕЩЁ» → «Флот и верфь»**, выбрать текстовую кнопку корпуса **«Открыть проект»**, затем передать материалы в окно верфи и нажать **«Построить и спустить на воду»**. Корабельный проект хранится отдельно от проектов зданий; верфь разрешает один текущий корабельный проект.

## Зафиксированная задача по интерфейсу строительства

Нужный игроку путь:

1. В «Строительство» показывать здания карточками с изображениями в сетке.
2. Нажатие на карточку здания открывает его описание и ресурсы; действие **«Начать строительство»** доступно, когда собраны нужные материалы.
3. После завершения строительства активная верфь добавляет вкладку **«Верфь»**.
4. Вкладка показывает корабли карточками с изображениями.
5. Нажатие на корабль открывает подробное окно с изображением, характеристиками и действием **«Построить»**.
6. Существующие системы продолжают проверять требования/допуски, снимать и возвращать материалы, создавать проект, завершать постройку и сохранять прогресс.

Для этого изменения сначала проверь существующие API из таблицы выше. Представления сейчас собраны GDScript-кодом. `data/ports/building_catalog.json` и `data/ships/ship_catalog.json` не задают изображения. Каталог спрайтов `assets/sprites/` пока не содержит готовых иконок зданий/кораблей; папки `assets/world/buildings/` и `assets/world/ships/` имеют README с планом для 3D-ресурсов. Значит, графические карточки потребуют добавить/подключить соответствующие UI-иконки, а не рассчитывать на уже готовый набор картинок.

## Сохранения и правила, которые нельзя обходить

- Мир детерминирован постоянным seed; генерация мира не должна перезаписывать открытые игроком порты, маршруты или другой прогресс.
- Всё runtime-состояние хранится в `GameState`. Все сохранения, миграции и чтение/запись файлов — через `SaveSystem`.
- Статические определения и баланс хранятся в `data/*.json`; не дублируй их константами в UI.
- Новые пользовательские действия оформляй системным API с результатом `{ok, message}`; UI вызывает этот API.
- Пользовательские сохранения нельзя удалять, сбрасывать или заменять тестовым состоянием.

## Проверка

В корневом `README.md` указана проверенная тестами версия Godot **4.4.1**. Обычный тестовый запуск:

```bash
GODOT_BIN=/path/to/godot bash tests/run_tests.sh
```

Скрипт тестов использует отдельный временный каталог данных пользователя. Не запускай тестовую сцену на обычном каталоге сохранений. Проверка Windows/Godot Editor и телефона выполняется отдельно; не заявляй о runtime-проверке без фактического запуска.

Перед завершением задачи проверь `git diff --check`, подходящие тесты и `rules/PROJECT_STATE.md`, если фактический статус механики изменился.
